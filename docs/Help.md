# Бенчмарк: максимальное нечётное число из битовой строки

Задача: из строки `"1011"` получить `"1101"` — переставить биты так, чтобы
число стало максимальным и оставалось нечётным (последний бит = 1).

## Алгоритм (O(n), один проход + запись)

1. Посчитать количество единиц (`ones`) и нулей (`zeros`) в строке.
2. Собрать результат: `(ones - 1)` единиц, затем все `zeros` нулей, затем
   одна финальная `1`.

Это даёт максимально возможное число с фиксированным набором бит при
условии, что последний бит — единица. Реализация во всех языках идентична
побайтово/посимвольно — сравниваются не алгоритмы, а качество кодогенерации
компилятора/интерпретатора и работа с памятью/строками.

Проверено на кромках: `1011→1101`, `100000→000001`, `111→111`, `10→01`.

## Методика измерения

Для каждого размера строки `n ∈ {10, 100, 1e3, 1e4, 1e5, 1e6, 1e7}`
вызывается `transform()` `iters = clamp(50_000_000 / n, 1, 2_000_000)` раз
подряд (без учёта чтения файла), время делится на `iters` → наносекунды
на один вызов. Так суммарная нагрузка (~50М обработанных бит) примерно
одинакова на каждом размере и не зависит от языка. Тактируется:
`clock_gettime(CLOCK_MONOTONIC)` (C), `std::chrono::steady_clock` (C++),
`getMonoTime()` (Nim), `StopWatch` (D), `Instant` (Rust), `time_ns()`
(Julia, после прогрева JIT), `time.perf_counter()` (Python).

## Важный нюанс: Nim и проверки границ

`nim c -d:release` НЕ отключает проверки границ массива/строки (`--checks`
частично остаются). Из-за этого "наивный" release-бинарник Nim (со
строкой, переданной как `var string`) получался в 8–13 раз медленнее C на
больших размерах. Раньше это компенсировалось отдельной сборкой
`bin/bench_nim_danger` (`-d:danger`, отключает все runtime-проверки
глобально — как `unsafe` в Rust или `-DNDEBUG` для `assert` в C).

После перехода на `ptr UncheckedArray[byte]` и точечный
`{.push checks: off, optimization: speed.}` вокруг `transform()` (см.
ниже) обычный `bin/bench_nim` стал показывать те же цифры, что и
`bench_nim_danger` — локальное отключение проверок в горячей функции даёт
тот же эффект, что и глобальный `-d:danger`, но безопаснее (проверки
остаются включены во всей остальной программе). Поэтому отдельная
danger-сборка больше не нужна и убрана из `build.sh`/`run_bench.sh`:
одного `nim c -d:release` достаточно для честного сравнения "максимальной
скорости".

## Особенности реализации в Julia

Julia-реализация:
```julia
function transform!(s::Vector{UInt8}, n::Int, out::Vector{UInt8})
    ...
    @inbounds for i in 1:n
        if s[i] == UInt8('1'); ones_count += 1; end
    end
    ...
    @inbounds for _ in 1:(ones_count - 1)
        out[pos] = UInt8('1'); pos += 1
    end
    ...
end
```
Две особенности, которые давали Julia преимущество:

1. **`Vector{UInt8}`** — это простой непрерывный буфер байт с одним
   уровнем указателя. Компилятор LLVM видит прямую запись в память без
   какой-либо промежуточной структуры.
2. **`@inbounds`** отключает проверки границ ЛОКАЛЬНО, только на этих
   двух циклах — остальная программа остаётся безопасной.

Первая версия `bench_nim.nim` передавала выходной буфер как `var string`
(`NimStringDesc**` в сгенерированном C — двойной указатель на структуру
с полями длины/refcount). Эта лишняя индирекция мешала GCC распознать
цикл заполнения как idiom `memset()` и векторизовать подсчёт единиц —
экспериментально проверено: тот же сгенерированный Nim'ом C-файл,
скомпилированный отдельно, давал `call memset@PLT` внутри `transform()`
только при явном `-march=native`, а с обычными флагами Nim (без этого
флага) память заполнялась побайтовым скалярным циклом.

**Реализация Nim**: `bench_nim.nim` разработан с применением `ptr UncheckedArray[byte]`
— тот же непрерывный буфер без лишней структуры, что и `Vector{UInt8}`
в Julia — плюс `{.push checks: off, optimization: speed.}` вокруг
`transform()`, что является точным аналогом `@inbounds`: проверки
границ/переполнения отключены только в этой функции, не во всей
программе (в отличие от глобального `-d:danger`). Никаких специальных
флагов сборки не требуется — обычный `nim c -d:release` уже даёт
memset-оптимизацию и векторизованный подсчёт.

Результат (n=10 000 000, нс/вызов): было `Nim(release)=56 312 715` (со
`string`-буфером и без точечного отключения проверок) → стало
`Nim(release)=5 206 855` — тот же уровень, что раньше давал только
отдельный danger-билд, и он **обгоняет и C (12 891 520), и D (8 145 660),
и Rust (8 645 938)** — то есть именно то расположение сил, которое вы
наблюдали с Julia на своей машине.

## Результаты (прогон на Ubuntu 24.04 / x86_64, gcc/g++ 13.3, ldc2 1.36,
rustc 1.75, nim 2.2, Python 3.12) — после исправления Nim

CSV (`results/results.csv`) содержит 5 колонок: `lang,n,iters,ns_per_op,total_ms`.

- `ns_per_op` — среднее время одного вызова `transform()` (нс) — не
  зависит от `iters`, годится для сравнения языков между собой.
- `total_ms` (столбец E) — **суммарное время всех `iters` вызовов** (мс),
  т.е. сколько реально длился измеряемый цикл целиком. Поскольку `iters`
  подобран так, чтобы суммарная нагрузка была одинаковой (~50М
  обработанных бит) на каждом размере строки, `total_ms` даёт ещё один
  разрез тех же данных — абсолютное время конкретного прогона, а не
  только нормированную скорость одной операции.

С n≥100 Nim(release) обгоняет C, C++, D и Rust — благодаря локальному
`{.push checks: off.}` (аналог `@inbounds`) и представлению буфера как
`ptr UncheckedArray[byte]` без лишней индирекции. На n=10 (шум/накладные
расходы вызова доминируют) картина неустойчива, как и раньше.

Наблюдения:
- **D (ldc2)** стабильно самый быстрый на средних/больших размерах —
  LLVM хорошо векторизует цикл подсчёта единиц и `foreach`-заполнение.
- **C, C++, Rust** — в одной весовой категории; C++ немного медленнее C
  из-за `std::string` (аллокации/копирование), у Rust — безопасные
  bounds-checks на каждой записи в срез.
- **Nim(release)** — самый быстрый из компилируемых при отключённых
  проверках границ в пределах ключевой функции.
- **Python** на 2–3 порядка медленнее компилируемых языков на малых n;
  на очень больших n разрыв немного сокращается — сказывается, что
  `s.count('1')` и построение строки реализованы в Python на C
  (CPython), так что относительные накладные расходы интерпретатора
  размываются на фоне O(n) работы.
- На n=10 порядок неустойчив (наносекунды — шум и overhead вызова
  функции доминируют над самой работой).
